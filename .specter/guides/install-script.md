# Install Script

**Tags:** install, setup, hooks, settings, deployment

`scripts/install.sh` is the single entry point for deploying the gone-fishing skill to a local Claude Code installation. It creates directories, copies all runtime files, writes the inline statusline script, and mutates `~/.claude/settings.json` with the four settings categories the skill requires. After it runs, the user only needs to invoke `/gone-fishing` once to assign a character; every subsequent session activates automatically. See [[architecture-overview]] for how all deployed pieces fit together.

## How to Run

From the repository root:

```bash
bash scripts/install.sh
```

No flags or arguments. The script uses `set -euo pipefail` so it aborts immediately on any error. It prints one progress line per operation.

## Operations, In Order

### 1. Resolve Paths

The script anchors all paths relative to its own location:

| Variable | Value |
|---|---|
| `REPO_ROOT` | Absolute path to the repository root |
| `CMD_SRC` | `$REPO_ROOT/.claude/commands/gone-fishing` |
| `CMD_DST` | `~/.claude/commands` |
| `DATA_DST` | `~/.claude/commands/refs/gone-fishing` |
| `STATUSLINE_SCRIPT` | `~/.claude/statusline-command.sh` |
| `HOOK_DIR` | `~/.claude/hooks` |
| `HOOK_SCRIPT` | `~/.claude/hooks/gone-fishing-session.sh` |
| `CATCH_HOOK_SCRIPT` | `~/.claude/hooks/gone-fishing-catch.sh` |
| `SETTINGS_FILE` | `~/.claude/settings.json` |

### 2. Create Directories

```bash
mkdir -p ~/.claude/commands
mkdir -p ~/.claude/commands/refs/gone-fishing/refs
mkdir -p ~/.claude/hooks
```

All three calls use `-p` and are safe to re-run. The `refs/` subdirectory is where the four [[persistence-layer]] runtime files (`profile.json`, `session.json`, `state.json`, `catches.json`) will live; install.sh creates the directory but never writes those files — they are created at runtime by Claude and the hooks.

### 3. Copy Skill .md Files

```
gone-fishing.md    →  ~/.claude/commands/gone-fishing.md
fishing-stats.md   →  ~/.claude/commands/fishing-stats.md
new-fisherman.md   →  ~/.claude/commands/new-fisherman.md
```

Source: `$REPO_ROOT/.claude/commands/gone-fishing/`. These Markdown files are the Claude Code slash-command definitions loaded when the user invokes `/gone-fishing`, `/fishing-stats`, and `/new-fisherman`.

### 4. Copy Data Files

```
fish.json       →  ~/.claude/commands/refs/gone-fishing/fish.json
fishermen.json  →  ~/.claude/commands/refs/gone-fishing/fishermen.json
```

Source: same `$REPO_ROOT/.claude/commands/gone-fishing/` directory. These are the bundled reference databases. Deploying them under `~/.claude/commands/refs/gone-fishing/` keeps them under the broad `Read` permission allowlist that install.sh adds to `settings.json`, so data-file reads never generate a permission prompt during a session.

If `fish.json` or `fishermen.json` are modified in the repository, install.sh must be re-run to propagate the changes to the deployed copies that Claude and the hooks actually read.

### 5. Copy and Chmod the Session Hook

```
scripts/gone-fishing-session-hook.sh  →  ~/.claude/hooks/gone-fishing-session.sh  (chmod +x)
```

This is the `UserPromptSubmit` hook. It fires before every user message and handles automatic session activation. See [[agentic-file-optimization]] for a full description of what the session hook injects.

### 6. Copy and Chmod the Catch Hook

```
scripts/gone-fishing-catch-hook.sh  →  ~/.claude/hooks/gone-fishing-catch.sh  (chmod +x)
```

This is the `Stop` hook. It fires after every Claude response, performs the 10% catch roll, selects a weighted fish, and writes `state.json` and `catches.json` atomically. See [[shell-catch-hook]] for the full hook flow.

### 7. Write the Inline Statusline Script

The script uses a heredoc to write `~/.claude/statusline-command.sh` in place, then `chmod +x`s it. This file is generated by install.sh directly — it is not copied from a source file in the repository.

#### What the Statusline Script Does

Reads a JSON blob from stdin (from Claude Code on each tick) with `model.display_name`, `context_window.used_percentage`, `effort.level`, and `thinking.enabled`. Constructs the base status string, then reads three runtime files:

| File read | What it extracts |
|---|---|
| `refs/session.json` | `fishermanName`, `activatedAt` |
| `refs/catches.json` | All `catches[].exp` values |
| `refs/state.json` | `state`, `caughtAt`, `catch.common`, `catch.ascii`, `catch.color` |

From `catches.json` it sums all `exp` values and derives level using `cumulative(n) = 25 * (n-1) * (n+2)` (iterating n from 2 to 50). From the level it derives rod tier as `floor((level-1)/5) + 1`, clamped to 10, then maps to an ANSI escape code applied to both the lure glyph `*` and the `Lv.NN` label. See [[leveling-system]] for the full tier-to-color table.

From `session.json` it checks whether `activatedAt` is within 28800 seconds (8 hours). The three-state glyph logic then follows [[animation-system]]:

| Condition | Glyph |
|---|---|
| `activatedAt` older than 8 hours | `~~~~~` (inactive) |
| Session active, idle or `caughtAt` age ≥ 120 s | `~~*~~` (lure in tier color) |
| Session active, caught and `caughtAt` < 120 s old | `~>!<~  <fish name> <ascii in ANSI 256-color>` |

Final output: `<model> | ctx:XX% | 🎣 <Name>  <glyph>  Lv.NN`

Because the statusline is written inline, changes to its logic require re-running install.sh.

### 8. Mutate settings.json

Modifies `~/.claude/settings.json` using `jq`. If the file exists, it updates in-place (atomic temp-file rename). If not, it creates the file from scratch.

#### The Four Mutations

**`statusLine`**
```json
{ "type": "command", "command": "/home/<user>/.claude/statusline-command.sh" }
```
Set unconditionally on every run.

**`permissions.allow`** — three entries appended and deduplicated with `unique`:
```
"Read(~/.claude/commands/refs/gone-fishing/**)"
"Write(~/.claude/commands/refs/gone-fishing/refs/**)"
"Bash(mv ~/.claude/commands/refs/gone-fishing/refs/*.tmp ~/.claude/commands/refs/gone-fishing/refs/*)"
```
These cover all data reads, atomic `.tmp` file creation, and the rename step respectively. Together they ensure zero permission prompts during a session. See [[persistence-layer]] for why `.tmp`-then-rename is used.

**`hooks.UserPromptSubmit`** — existing entries matching the session hook command path are removed, then the entry is appended. Idempotent by command path.

**`hooks.Stop`** — same deduplication logic for the catch hook entry.

## When to Re-Run

| Change | Re-run needed? |
|---|---|
| `fish.json` or `fishermen.json` updated | Yes — deployed copies must be refreshed |
| Hook scripts (`*-session-hook.sh`, `*-catch-hook.sh`) updated | Yes — deployed copies must be refreshed |
| Skill .md files updated | Yes — deployed copies must be refreshed |
| Statusline logic changed (in install.sh itself) | Yes — inline script is overwritten on each run |
| Fresh machine / new `~/.claude` directory | Yes — initial install |
| `settings.json` manually edited to remove gone-fishing entries | Yes — to restore hooks and permissions |

Catch history, active fisherman, session state, and fish state all live in `refs/` and are **never touched by install.sh**. Re-running the script does not reset any user data.
